# STEPS 1.0.0 Product Target and Readiness Assessment

**Status:** Proposed product contract; not an owner-approved release commitment.

**Assessment date:** 2026-11-18.

**Repository baseline:** `main` at `3fe4b8acefe99acfdb66a0d559de66949dc0affc`.
**Current release:** `v0.1.0`. **Development version:** `0.2.0-dev` / `0.2.0.dev0`.

> **Decision boundary:** STEPS 1.0.0 has not been defined or scheduled in an accepted ADR. This document distinguishes observed code and release evidence from a proposed product contract. A passing test, an implementation, an owner decision, a human theory review, and a public release are different kinds of evidence.

## Executive assessment

STEPS is no longer only a theory library or an empty desktop scaffold. The repository contains a tested music-theory core, a progression session and controller, a Tkinter two-area desktop prototype, project persistence primitives, and Standard MIDI File (SMF) export. A GitHub release `v0.1.0` exists. The current development version is `0.2.0-dev`.

That evidence does **not** establish a complete, installable, internationally supported desktop product. The UI now exposes localized add/edit/remove and undo/redo actions, project dialogs, analysis, and MIDI export, but does not yet expose every proposed product setting or provide platform acceptance. Cross-platform native acceptance, packaging/release automation, documentation parity, and a 1.0 owner-approved scope are not established by the current repository snapshot.

The recommended 1.0 product is a focused, local-first progression workspace for producers who want to create and transpose chord progressions, inspect context-dependent theory, preserve notation choices, save projects, and export standard MIDI. This recommendation follows the accepted v0.1 direction in [ADR-013](../../decisions/ADR-013-v01-umfang-akkorde-und-midi-export.md); it is not itself an accepted decision. Keep live audio and drum editing out of 1.0 unless the owner explicitly revises the existing scope decision that places drums in app v2.

### Public-description corrections required

The root README and [implementation status](../IMPLEMENTATION.md) must not say that the desktop entry point, project persistence, or MIDI export do not exist. The accurate distinction is:

- **Exists:** a desktop prototype and a testable core/controller path for editing, saving/loading, and MIDI export.
- **Still required for a product claim:** complete user-facing project commands, reliable error/confirmation flows, language selection, packaged installation, supported-platform acceptance, and external MIDI interoperability evidence.
- **Not in the current v0.1 scope:** in-app audio playback, as recorded by [ADR-007](../../decisions/ADR-007-audio-nur-dateiexport-v01.md).

## Proposed 1.0 product contract

### Primary user outcome

A producer can create or edit a short chord progression, choose the tonal context and notation convention explicitly, inspect a useful and appropriately qualified explanation, transpose without losing musical intent, save and reopen the project, and export a standard MIDI file that imports correctly into supported external software. The workflow is available in English and German. Changing the UI language never changes note spelling, pitch, project values, or any other musical data.

This is a product hypothesis to validate. It is not a claim that STEPS has already demonstrated user success.

### Recommended scope

1. **Progression editing:** create, reorder, edit, and remove chords; expose key, mode, tempo, meter, and relevant event timing with understandable validation.
2. **Contextual theory:** show what is deterministic, what depends on a chosen framework or style context, and which alternative interpretations remain plausible. Never present one global interpretation as universally correct.
3. **Notation and voicing:** preserve enharmonic spelling and distinguish sounding pitch, pitch class, note spelling, chord identity, symbol, voicing, inversion, and function. Keep German `H/B` and international `B/Bb` explicit.
4. **Project files:** save and reopen through the application; preserve musical data across UI-language changes; document schema compatibility and recovery behavior.
5. **MIDI export:** export deterministic SMF with documented timing, note-off, track, channel, and spelling semantics. Verify representative exports in at least two independent applications before claiming interoperability.
6. **Learning content:** publish only source-bound content whose relevant claims and language versions have separately recorded review states.
7. **International interface:** ship English (`en`) and German (`de`) UI catalogs, an English fallback for unsupported system languages, an explicit `system`/`en`/`de` preference, and testable runtime language changes. The UI-language preference is independent of notation convention.
8. **Distribution and support:** publish installation instructions, supported platform/version bounds, security contact, license and third-party notices, release notes, and known limitations for the exact release.

### Proposed non-goals

- Live audio playback or a full DAW.
- Audio-to-chord recognition or automatic key detection.
- Cloud accounts, collaboration, or a required network service.
- Broad production-library coverage or publication of unreviewed research.
- Drum editing in 1.0 unless the owner revises the accepted v2 deferral in ADR-013.

These are scope recommendations, not new accepted ADRs. A future release may add them without weakening the 1.0 quality gates.

## Release decision and definition of done

The 1.0 tag should not be created until:

- The owner has accepted the scope and compatibility contract in an ADR.
- Every included product claim maps to implemented code and an executable test or documented manual acceptance.
- The main user workflow is available through the shipped interface, not only through a Python API or controller test.
- `en` and `de` are complete for the release UI; language switching and persistence are verified independently of notation.
- Project round-trip/migration and MIDI export/interoperability gates pass.
- Required source reviews, licensing, third-party notices, security, and accessibility reviews are complete or explicitly block the affected feature.
- English release notes and the promised German information are reviewed; versions, changelog, catalogs, docs, and artifacts refer to the same release commit.
- The release candidate has CI evidence and explicit human approval. Published tags are immutable.

For any unmet criterion, report `BLOCKED`, `NOT_RUN`, or `NOT_EVIDENCED`; do not turn an absence of evidence into a pass.
